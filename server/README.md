# Login + "edit your own profile" backend

Lets the person a profile belongs to log in and edit their own page
directly — see `SYSTEM_OVERVIEW.md` §7 for how it fits into the rest of
the pipeline and exactly what it does and doesn't let someone change.

## One-time setup

```bash
cd server
npm install
```

For production (running via the systemd unit in `deploy/profile-backend.service`),
the secret lives in `/etc/profile-backend.env` — deliberately **outside**
the git repo, so a `git pull`/checkout/clean can never wipe it (this bit us
more than once when it lived at `server/.env`):

```bash
SECRET=$(node -e "console.log(require('crypto').randomBytes(48).toString('hex'))")
sudo tee /etc/profile-backend.env > /dev/null <<ENV
AUTH_JWT_SECRET=$SECRET
PORT=3000
NODE_ENV=production
MYMEMORY_EMAIL=
ENV
sudo chmod 600 /etc/profile-backend.env
sudo chown root:root /etc/profile-backend.env
```

`server/.env.example` is still there as a reference for what keys exist and
what they do — just don't rely on `server/.env` itself surviving a redeploy.
For quick local testing outside systemd, `server/.env` (loaded manually,
e.g. `set -a; source .env; set +a; node index.js`) is fine — just know it's
git-ignored and won't persist across a fresh checkout, which is exactly why
production doesn't use it.

## Create a login for a profile

One account per already-approved profile (there's no public self-signup):

```bash
node create-user.js <profileKey> <username> <password>
# e.g.
node create-user.js ahmed-mohamed ahmed 'a-strong-password-123'
```

`<profileKey>` is the URL slug — the same thing that appears as
`data/profiles/<profileKey>.json` and as `/p/<profileKey>/` on the live
site. Re-running this command for the same username updates its password
(or re-points it at a different profileKey) — that's also how you reset a
forgotten password, since there's no self-service "forgot password" email
flow.

Give the resulting username/password to that person directly.

## Run it

```bash
AUTH_JWT_SECRET=... node index.js
# Public site: http://localhost:3000/
# Login:       http://localhost:3000/login
# Edit:        http://localhost:3000/edit
```

For anything beyond local testing, run it under something that restarts
it on crash/reboot — pm2 (`pm2 start index.js --name profile-backend`) or
a systemd unit are both fine. Set `NODE_ENV=production` once you're
serving over real HTTPS (it makes the session cookie HTTPS-only).

## Deploying alongside nginx

You don't have to route the whole site through Node. The updated
`deploy/nginx-tutor-portfolio.conf` keeps serving `site/` as plain static
files and only proxies `/api/`, `/login`, and `/edit` to the Node process
on `127.0.0.1:3000`. If you'd rather run everything through Node instead,
`index.js` also serves `site/` itself — just point your reverse proxy (or
nothing, for local use) at it directly.

## What a logged-in user can and can't do

They can edit every section of **their own** profile: name, title,
summary, theme, teaching/professional details, education, languages,
videos (including pasting a new YouTube/Drive link), certificates
(including a new file link), skills, and contact info.

They can't: change their `profileKey` (the URL slug), switch `kind`
between tutor/professional (that changes which sections render at all),
or touch `status`/`visibility`/`featured` — those stay behind the
CSV-approval gate described in `SYSTEM_OVERVIEW.md` §3, and they can't
see or edit anyone else's profile — every API route acts on "my own
profile" from the session, never on a profile key supplied by the client.

## Files

- `index.js` — the Express app and every route.
- `create-user.js` — admin CLI, see above.
- `lib/auth.js` — session signing/verification (JWT) + cookie settings.
- `lib/users.js` — reads/writes `users.json` (bcrypt password hashes).
- `lib/profile-store.js` — applies an edit, re-renders the page, keeps
  `data/index.json` in sync. Reuses `scripts/build-site.js`'s renderer and
  `scripts/lib/parse.js`'s media-link handling, so a pasted video/photo
  link is treated exactly the same way here as in the CSV pipeline.
- `public/login.html`, `public/edit.html` + `edit.js` + `edit.css` — the
  two pages themselves, plain HTML/JS, no build step.
- `users.json` — generated by `create-user.js`. Contains password hashes;
  git-ignored on purpose. Back it up separately if you care about not
  re-creating accounts after a redeploy.
